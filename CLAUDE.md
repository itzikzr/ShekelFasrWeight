# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Tkinter desktop weighing station for a Swan scale head over RS-232 Serial, cross-platform (Windows + Linux). The conveyor/scale runs continuously; when a weight crosses a threshold the app averages the incoming stream and, once the item leaves the scale, records the settled weight — classified green/red/yellow against a selected product's target weight and tolerances. Every weighing and every product is persisted to a local SQLite database.

`scale_sampler.py` is a thin entry point; all logic lives in the `scale_app/` package.

## Running

```bash
pip install pyserial
python scale_sampler.py
```

Windows: double-click / run `run.bat`. Linux: `./run.sh` (both install `pyserial` if missing; `run.sh` also checks for the `tkinter` system package, which isn't pip-installable — e.g. `sudo apt install python3-tk` on Debian/Ubuntu, `sudo dnf install python3-tkinter` on Fedora).

`openpyxl` is an optional dependency (also auto-installed by `run.bat`/`run.sh`), needed only for the "ייצוא לאקסל" button in `weighing_detail_window.py`; everything else runs fine without it, and that one button just shows an error message pointing at `pip install openpyxl` if it's missing.

There is no test suite, linter, or build step — verification is manual: run the app against a real or simulated Swan head, or exercise `scale_app.main_window.MainWindow` headlessly (`root.withdraw()`) and call `_on_session_done(...)` directly with synthetic readings to drive the decide→classify→DB pipeline without hardware (this is how the current implementation was verified).

Two files are gitignored, local machine state — never commit them:
- `scale_sampler_config.json` (port, baud, thresholds, last-selected product) — loaded on startup, saved whenever a setting changes.
- `scale_data.db` (SQLite — all products and all weighings).

### Launch at OS login (opt-in — a Settings checkbox, not a default)

`scale_app/autostart.py` is the single source of truth: `is_enabled()`/`enable()`/`disable()`, platform-dispatched. Windows creates a `run.bat` shortcut in the current user's Startup folder (`%APPDATA%\...\Startup`) via a `WScript.Shell` COM call shelled out to PowerShell (no simpler stdlib way to write a `.lnk`); Linux writes/removes the XDG-standard `.desktop` file at `~/.config/autostart/`. `SettingsWindow`'s Connection tab shows a "הפעלה אוטומטית עם עליית המחשב" checkbox (only if `autostart.is_supported()`) reflecting and toggling this — `_on_autostart_toggle()` catches failures and resyncs the checkbox from the real on-disk state rather than trusting the click.

The standalone `install-autostart-windows.bat`/`uninstall-autostart-windows.bat` and `install-autostart-linux.sh`/`uninstall-autostart-linux.sh` (repo root) do the exact same thing non-interactively, for headless/offline setup (e.g. while provisioning the NUC before the app has ever been launched) — they write to the **identical** paths/filenames as `autostart.py` on purpose, so the checkbox and the scripts never fight each other or create duplicate entries.

### Threading contract (extended from the single-file version)

`WeighingEngine` (`engine.py`) owns the `pyserial` connection and runs every background thread — none of them ever touch Tk. They only push `(kind, payload)` tuples onto a `queue.Queue`. `MainWindow._pump_queue` (`main_window.py`), scheduled via `root.after(40, ...)`, is the **only** place that drains the queue, touches widgets, **and writes to SQLite**. This extends the original rule ("threads never touch Tk") to also cover the database, so no `sqlite3` connection ever needs `check_same_thread=False` or locking.

This matters specifically for verdict classification: the continuous monitor thread (`WeighingEngine._monitor_loop`) runs for the entire life of the connection, spanning many weighing sessions, so the operator can change the selected product between sessions. The engine thread therefore reports only the raw decided result (`"session_done"`: readings, elapsed, wall-clock start/end) — `MainWindow._on_session_done` reads whichever product is *currently* selected, calls `db.classify()`, and writes the row.

Threshold/debounce/listen-mode/show-each are **not** Tk vars read once at thread start — they live in `EngineSettings` (plain attributes), written by the main thread when Settings is saved and read every loop tick by the engine thread. This is a deliberate, narrow exception that lets an operator tune the trigger threshold live without reconnecting; it's safe only because the values are simple floats/bools (atomic under the GIL), never Tk objects.

`engine.decide_weight()` is the same flat-window algorithm as before (slides a window of 6 readings, picks the lowest-stdev window, returns its median) — now a standalone function reused by the monitor loop and both diagnostics threads. It returns `(decided, basis, window_start, window_end)` — the last two are the `[start, end)` index range into `readings` that was actually used, so callers can mark which raw readings fed the decision (see below).

**Candidate readings are restricted to `> PEAK_FRACTION_FLOOR` (50%) of the session's peak weight before the flat-window search runs.** Without this, a short dwell time (item pulled off the scale quickly after settling) can make the quiet/empty tail *after* the item was removed statistically flatter than the brief real plateau — the old unrestricted search would then confidently "decide" ~0 instead of the actual weight. This was found and fixed from real exported weighing data (sessions with a long dwell decided correctly either way; short-dwell sessions decided ~0 before this fix and the correct weight after). Falls back to the median of whatever candidates exist (or all readings, if none clear the floor) when fewer than 6 readings qualify.

### Conveyor relays/sensors (`relay_engine.py`, opt-in) — IA-3116-U2i card

A completely separate serial device (its own port/baud, its own protocol) from the Swan scale — a 16-relay + 16-isolated-digital-input card, wired to the conveyor. Reference: `REL/IA-3116-U2i_UM.pdf`. ASCII command protocol, fixed device address `00` (no multi-card chaining yet): `?002<CR>` polls status, returning 8 hex chars `ABCDEFGH` — nibble `D` (index 3) bit0/bit1 are input1/input2, nibble `H` (index 7) bits 0-3 are relay1-4; `!aa3dd<CR>`/`!aa4dd<CR>` activate/deactivate a single relay (`dd` = relay number − 1, in hex).

**How the three relay-tied features map onto this app's existing concepts:**
- **Relay 1 — conveyor motor, and (in one sub-mode) the weighing "arm" switch.** `MainWindow`'s "▶ התחל"/"⏹ עצור" header button, `_on_relay_motor_toggle`. Clicking "התחל" (not "עצור") auto-connects *both* devices first if either isn't connected yet — the scale itself (`self.connect`, same as the header's own "התחבר" button) and the relay card (`self.connect_relays`), each using its own saved port/baud — instead of just erroring and redirecting to Settings; only falls back to that error if a device has no port saved yet, or its connect attempt itself throws (and in that case the motor never actually turns on). Clicking "עצור" never disconnects either device. See `EngineSettings.armed` below for the second thing this button controls.
- **Input 1 (closed→open edge) — start weighing.** Fires `RelayEngine.on_input1_edge` → `WeighingEngine.force_start_session()`, a plain boolean flag (`_pending_force_start`) checked every `_monitor_loop` tick — same cross-thread-safe-without-a-lock pattern as `EngineSettings` (simple atomic types, GIL-protected). Only actually used when "השתמש בכניסות (INPUT)" is on — see below.
- **Input 2 (open→closed edge) — stop weighing + trigger sorting.** Fires `on_input2_edge` → `force_stop_session()` (`_pending_force_stop`), *and*, once the resulting `session_done`/verdict reaches `MainWindow._on_session_done()`, `RelayEngine.activate_sort_relay(verdict)` (relay 2=yellow, 3=green, 4=red) — pulses for `RelaySettings.sort_pulse_seconds` (Settings → ממסרים), or gets cut short immediately if the *next* box's sort event arrives first, so only one sort relay is ever on at a time. Sorting fires from `_on_session_done` unconditionally whenever relays are connected — it doesn't care whether the session that just ended was sensor-driven or threshold-driven, so it works identically in both sub-modes below.

**Two independent settings gate all of this, not one.** `relay_enabled` ("השתמש בממסרים") is the master switch — relay 1/motor button and relay 2-4/sorting only exist at all when this is on *and* the card is actually connected (`active = relay_enabled and relay_engine.connected`, computed once in `MainWindow._sync_relay_sensor_mode()`). Within that, `relay_use_inputs` ("השתמש בכניסות (INPUT) לכניסה/יציאה") — a *separate* checkbox, same tab — picks which of two sub-modes drives weighing start/stop:
- **On** (default, preserves this feature's original behavior): `EngineSettings.use_relay_sensors = active and relay_use_inputs` — input1/input2 edges drive start/stop exactly as described above, weight threshold is bypassed entirely.
- **Off**: `EngineSettings.require_armed = active and not relay_use_inputs` instead — weighing reverts to the *original* weight-threshold/debounce state machine, but a session can only **start** while `EngineSettings.armed` is true (`_monitor_loop`'s IDLE branch: `gate_ok = (not require_armed) or armed`, then `start_now = gate_ok and w > threshold`) — i.e. "התחל" is a literal ignition key: relay 1 on **and** weighing armed are the same action (confirmed with the user as the intended reading of "כפתור שמחליף מצב" applied to this sub-mode). Stopping a session in this sub-mode still uses the plain threshold/debounce logic, unaffected by `armed` — only the *start* edge is gated. `armed` mirrors `MainWindow._relay_motor_on` (set in `_sync_relay_sensor_mode()`, called after every motor toggle and after `relay_connection_lost`/`disconnect_relays` reset `_relay_motor_on` back to `False`, since the on-wire relay state is unknowable once the port drops).

This gives a real, useful third configuration beyond "sensors" and "off": sorting relays + a manual motor button, without trusting/wiring entrance-exit sensors at all — weighing still needs to be manually armed via Start, but its start/stop timing is the same threshold logic that's been verified since before this feature existed.

**All relay-port access is serialized through one thread** (`RelayEngine._poll_loop` — polls `?aa2` in a loop, and drains a `_pending` command list between polls) for the same reason `pause_device_access()` exists for the scale: two threads hitting one serial port concurrently steal each other's bytes. `set_relay()`/`activate_sort_relay()` (called from the main thread) never write to the port directly — they only append to `_pending`; the poll thread performs the actual write on its next iteration (worst case one `POLL_INTERVAL`, 50ms, of latency).

**The whole feature is invisible until opted into.** `MainWindow.relay_enabled` (Settings → ממסרים checkbox) starts `False`; while it's off, the header motor button is unpacked (not just disabled — `_sync_relay_ui()`), `use_relay_sensors`/`require_armed` stay `False`, and nothing about the dashboard's appearance or the weighing state machine changes from before this feature existed. Persisted alongside `relay_port`/`relay_baud`/`relay_use_inputs`/`relay_sort_pulse_seconds` in `scale_sampler_config.json`, same pattern as the scale's own `port`/`baud`. `relay_use_inputs` defaults to `True` (not `False`) specifically so that a config file saved before this checkbox existed keeps its original all-sensor behavior on upgrade, rather than silently switching to the new armed/threshold sub-mode.

### "Recent weighings" dashboard list — time filter and non-destructive clear

The left-panel Treeview is filtered, not just appended-to: `MainWindow._recent_since_bound()` computes a `since` timestamp from the picked filter (`RECENT_FILTERS`: today / last 7 days / since this app session started, tracked via `self._app_start_time`) and `db.list_weighings(since=...)` does a plain `timestamp >= ?` string comparison — safe because `db.insert_weighing()` always writes `datetime.isoformat(timespec="seconds")`, so lexicographic and chronological order agree. "נקה תצוגה" (clear display) does **not** touch the DB — it just sets `self._recent_cleared_at = datetime.now()`, which `_recent_since_bound()` folds in as a floor (`max(filter_bound, cleared_at)`) so the list re-filters to empty *without deleting anything*; the same rows are still visible in `HistoryWindow`/CSV export, and new weighings still append live afterward since a session's timestamp is always ≥ any of these bounds. Picking a filter again (`_on_recent_filter_changed`) resets `_recent_cleared_at` back to `None` — otherwise a clear would keep suppressing everything forever, even after the operator explicitly asks to see a wider range like "השבוע" again. `MainWindow._refresh_recent_list()` is the one place that re-queries and repopulates the tree (on startup, on filter change, and after clearing) — `_add_recent_row()` (called from `_on_session_done`) still does an unconditional `insert(..., 0, ...)` for a just-completed weighing rather than going through the filter, since "just happened" always satisfies whatever bound is active.

The filter combobox is another instance of the display/logical-value split documented in `rtl.py` above (`self._recent_display_to_key`) — its labels are Hebrew, bidi-reordered for display on Linux, and the read-back selection is translated back to the internal `"today"/"week"/"session"` key before use, same pattern as `product_combo`/`history_window`'s filters.

**Product summary table** (below the weight/`ColorBar`, right panel): `MainWindow._refresh_product_summary()` aggregates green/red/yellow/total counts per `product_name` over the *exact same* `since` bound as the recent list (`_recent_since_bound()`), so it always reflects whatever the left-panel filter/clear state currently shows, not all-time totals. It's called from `_refresh_recent_list()` (covers startup/filter-change/clear) and once more explicitly from `_on_session_done()`, since a live just-completed weighing goes through `_add_recent_row()`'s incremental insert rather than a full `_refresh_recent_list()` — without that second call the summary table would lag one weighing behind the list next to it.

### Scale device configuration (`SettingsWindow`'s "פרטי מכשיר" / "הגדרות משקל" / "איפוס יצרן" tabs)

`Swan_SC_Protocol.md` (repo root) is the authoritative reference for the scale's own direct single-character commands (`F`/`B`/`R`/`Q` query-then-set-digit menus, `Z`/`T`/`C` actions, `I`/`V`/`A` read-only queries) — distinct from `SettingsWindow`'s "חיבור"/"שקילה" tabs, which only cover *this app's* connection/threshold settings, never the scale's own NVRAM. Originally a separate `ScaleConfigWindow` Toplevel; merged into `SettingsWindow` as three more Notebook tabs — `tab_device_info` (read-only Info/Version/raw AD), `tab_scale_config` (full scale/rounding/disform/baud + zero/tare/clear-tare), `tab_factory_reset` — split into this many rather than one dumping-ground tab so each screen stays short. `WeighingEngine` exposes one method per command (`query_full_scale`/`set_full_scale`, `zero`, `get_info`, …), each spawning its own thread guarded by `self._device_busy` so two device commands can never race on the port; all share the `_read_until()` helper (also used by calibration). Each parameter row has its own "קרא" (read) button calling its query method directly — nothing is queried automatically on open or in bulk; the user reads whichever parameter they want, whenever they want, one at a time (`_run()` just sets busy and fires the one command).

**Pause/resume is scoped to *tab-active time*, not the whole Settings window's lifetime** — this is the one real behavioral difference from the old standalone-window design, and matters: `SettingsWindow` is opened far more casually/often than the old dedicated screen ever was (just to flip a threshold, check the port, etc.), so pausing continuous weight streaming for its entire lifetime would freeze the main dashboard's live weight display every time someone opens Settings for something unrelated. Instead, `SettingsWindow._on_tab_changed()` (bound to the Notebook's `<<NotebookTabChanged>>`) calls `pause_device_access()` only when switching *into* `tab_device_info`/`tab_scale_config`/`tab_factory_reset`, and `resume_after_device_access()` when switching to any other tab or on window close (`destroy()`) — tracked via `self._device_tab_active`, which stays `True` across moves *between* those three tabs (no redundant re-pause/resume churn when hopping from "פרטי מכשיר" to "הגדרות משקל"). `MainWindow`'s own header "↺ איפוס" button (sends `Z` directly, bypassing the tab) checks `_settings_device_tab_active()` before touching pause/resume itself, so it doesn't fight with an already-paused Settings tab if both happen to be relevant at once — see the `"device_zero"` dispatch in `MainWindow._pump_queue`, which forwards to *both* `MainWindow._on_zero_result` and `SettingsWindow.handle_engine_event` (the tab's own Zero button and the header button share the same engine event, and each independently no-ops around the other via that guard).

**`baud_var` name collision, already fixed once — don't reintroduce it.** The Connection tab's `baud_var` (this app's serial port baud) and the device-config tab's baud (the *scale's own* NVRAM baud, read/written via `B`) are two unrelated settings that briefly shared the same attribute name after the `ScaleConfigWindow` merge, since both build methods run in the same `__init__`. The second assignment silently clobbered the first, leaving the Connection tab's combobox bound to an empty `StringVar` — invisible until `connect()` called `int(baud_var.get())` and crashed with `invalid literal for int() with base 10: ''`. Fixed by renaming the device-side one to `device_baud_var`/`device_baud_combo`. Any future device-config field whose name might plausibly clash with an app-level setting (baud, port, etc.) needs an equally distinct name — this class has no per-tab namespacing to catch it for you.

Two destructive paths are behind explicit confirmation, per user sign-off before this feature was built: **baud-rate change** (`set_baud`) reboots the scale and silently strands the app at the old baud until the operator reconnects at the new one in the "חיבור" tab — gated by a `messagebox.askyesno` warning before sending. **Factory reset** (`factory_reset`, ESC D) wipes all scale NVRAM (calibration, full scale, baud, everything) — gated by requiring the literal text `RESET` typed into a field before the button even enables, *plus* a confirmation dialog, and lives on its own separate tab (not just a red-bordered subsection) specifically so it takes one more deliberate click to even reach. `factory_reset()` emits `"device_reset_disconnect"` afterward, handled by `MainWindow` exactly like calibration's `"calib_disconnect"`.

**ESC-terminator case note**: `Swan_SC_Protocol.md` documents ESC sequences ending in uppercase `E` (`ESC D ESC E`), but the calibration wizard's already-hardware-verified code (predating this doc) uses lowercase `e` (`\x1B\x65`). `factory_reset()` deliberately matches the working calibration code's lowercase terminator, not the doc — if a future protocol update confirms uppercase is actually required, verify against real hardware before "fixing" this back.

**`pause_device_access()` / `resume_after_device_access()`, not raw `stop_monitor()`/`start_monitor()`**: both the device-config tabs and the calibration dialog must silence the scale's actual continuous broadcast (send `s`) before talking to it in request/response mode, not just stop the app's own read loop — in listen mode the scale keeps streaming weight packets regardless of whether anything in the app is reading them, and those stray packets interleave with command responses and defeat `_read_until()`'s idle-timeout detection (it never sees a quiet gap, so every command runs to its full multi-second timeout instead of returning as soon as the real response arrives). `pause_device_access()` also `.join()`s the monitor thread (via `stop_monitor(wait=True)`) instead of just flipping a flag, closing a race where the monitor could still be mid-read when device commands start writing to the same port. `resume_after_device_access()` resends `S` (if listen mode) and restarts the monitor. Any future code path that sends direct scale commands must pause/resume through these, not `stop_monitor()`/`start_monitor()` directly.

**Linux-only: `_write()` calls `conn.flush()`, and `pause_device_access()` sleeps 0.2s + re-flushes after sending `s`.** Legitimate defensive fixes (without an explicit `flush()`, a serial `write()` only queues data with the OS and returns — timely transmission isn't guaranteed the way it is on Windows), kept because they're correct regardless — but see the finding below before assuming they fix a given symptom.

**⚠ Confirmed on real hardware (NUC8CCHK, Ubuntu 24.04): this specific Swan unit does not implement the SC command set at all.** Every device-config "קרא" button returned a completely empty response — no data, not even stray stream noise — while continuous weight streaming on the same port/baud worked fine. Chased this through several *plausible but wrong* hypotheses first (ModemManager probing the port — ruled out via `journalctl -u ModemManager`, it never touched this device; a stale/renumbered `/dev/ttyUSB*` node after repeated unplug/replug — ruled out by reconnecting fresh and re-confirming live weight; the app's own monitor thread not truly stopping — ruled out by observing the main-screen weight readout freeze solid while the tab was open). The decisive test bypassed the app entirely: `picocom -b 9600 /dev/ttyUSB1`, typed by hand — `s` and `W` worked exactly as documented, but *every other command* (`I`/`V`/`F`/`B`/`R`/`Q`/`Z`/…) got no response whatsoever. So this unit's firmware only implements the base weight-streaming protocol (PC0034), not the SC extension — a software fix cannot change that. If device-config reads mysteriously return nothing on a *different* unit, don't assume it's this same firmware gap — re-run the ModemManager/flush/settle checks above first, since those are real, independently-worth-having fixes for genuinely different failure modes.

**Real-hardware response quirks (found from captured serial logs, not just the doc)**: `Swan_SC_Protocol.md`'s placeholder notation is misleading in places — `query_baud()` parses `Baud=XXXXXXX` as the *actual current baud rate* (e.g. `9600`), not a 0–7 menu index like the doc's single-`X` placeholders for `Round`/`Disform` might suggest; a real unit also reported `Disform=008`, outside the documented 0–5 range for that menu. `SettingsWindow._safe_label()` guards every menu-index-to-label lookup (rounding, disform, and the `set_baud`-confirmation path) against out-of-range values — it shows the raw number instead of indexing off the end of the list. This guard is load-bearing: an unguarded `LABELS[index]` raising `IndexError` inside `handle_engine_event` (called from `MainWindow._pump_queue`) would skip that call's `root.after(40, self._pump_queue)` reschedule and silently freeze the *entire app's* UI updates, not just that one field — so any new indexed lookup added here needs the same bounds-checking, and `_pump_queue`'s per-message dispatch should stay resilient to a single bad/unexpected device response.

**Linux only — ModemManager can interfere with device commands, but wasn't the cause here**: still worth having. ModemManager probes every new USB-serial device with AT commands to check if it's a cellular modem, which *can* race with request/response exchanges on the same port (passive continuous reads are far less affected). Guarded against with a udev rule (`udev-rules/99-swan-ftdi-ignore-modemmanager.rules`, tagging the exact FTDI `idVendor:idProduct` — `0403:6015` for this hardware — with `ID_MM_DEVICE_IGNORE=1`) rather than anything in `engine.py`; `install-linux.sh` installs it automatically. If a different USB-serial chip is ever used, the rule's `idVendor`/`idProduct` must be updated to match (`lsusb` to find them).

### Diagnostics live under Settings, not the main screen

The old one-shot "sample for N seconds" and "LIVE" modes are diagnostic tools for verifying wiring/protocol, not part of normal operation — they're on the **Diagnostics** tab of `SettingsWindow`, backed by `WeighingEngine.sample_once()` / `start_live()`/`stop_live()`. The Swan PC0035 calibration wizard (`WeighingEngine.start_calibration()` + `CalibrationDialog` in `settings_window.py`) is also there. Opening the calibration dialog calls `stop_monitor()` first (calibration and continuous monitoring can't share the port at once) and resumes monitoring on cancel/error; a successful calibration ends with the scale rebooting, which the engine signals via a `"calib_disconnect"` event that `MainWindow` turns into a real `disconnect()`.

### Database (SQLite, stdlib `sqlite3`, `db.py`)

Two tables: `products` (name, target_weight, tolerance_upper, tolerance_lower) and `weighings` (one row per completed session — decided weight, a **snapshot** of the product's name/target/tolerances at the time, verdict, reading count, elapsed, min/max, decision basis). The snapshot means history stays meaningful even if a product is later renamed or deleted.

`db.classify(weight, target, tolerance_upper, tolerance_lower)` is the traffic-light rule: `red` if `weight > target + tolerance_upper`, `yellow` if `weight < target - tolerance_lower`, else `green`. A weighing recorded with no product selected gets verdict `"none"`.

A third table, `weighing_readings`, stores the raw `(t_offset, weight, in_window)` samples behind each weighing so `WeighingDetailWindow` can show them on double-click — `in_window=1` marks the readings inside the flat window `decide_weight()` actually used, rendered in green. Storing every raw reading forever would grow unbounded, so `db.insert_weighing_readings()` prunes down to the `db.DETAIL_RETENTION_COUNT` (100) most recent weighings-with-detail after every insert; the aggregate `weighings` row is never pruned, only its raw-reading backing data — so old entries in the recent list / History still show correctly, just without a detail view (`WeighingDetailWindow` shows a message instead of an empty table in that case).

**IMPORTANT — test isolation footgun**: `db.connect(db_path=None)` falls back to the module-level `DB_FILE` *read inside the function body*, specifically so that reassigning `db.DB_FILE` (e.g. in tests) works. Do not change this back to a `db_path=DB_FILE` default — a default argument is evaluated once at import time, so a default bound that way silently ignores any later reassignment of `DB_FILE` and a parameterless `db.connect()` call (e.g. from `MainWindow.__init__`) keeps hitting the real project `scale_data.db` even when a test believes it redirected it. When testing this app headlessly, prefer passing `db_path=` explicitly (and monkeypatching `db.connect` itself if code under test calls the parameterless form) over reassigning `db.DB_FILE` and hoping.

### Light/dark mode

`theme.py` holds two color dicts (`_LIGHT`/`_DARK`) and mutates its own module-level color constants (`BG`, `CARD_BG`, `TEXT`, …) via `_apply_palette(mode)`. `theme.set_mode(root, mode)` swaps the palette and re-runs `apply_theme(root)`, which re-configures the shared `ttk.Style()` — that alone is enough to live-update every ttk widget, since they all read colors from the style rather than fixed instance options.

It is **not** enough for plain `tk.Label`/`tk.Canvas`/`ScrolledText` widgets (the big weight readout, `ColorBar`, `StatusPill`, log boxes) or for `ttk.Label`/`Treeview` instances that were given an explicit per-instance `foreground=`/tag color at creation — those bake the color in and never re-read the style. Every screen that owns such a widget therefore exposes a `refresh_theme()` method that reconfigures them from the (now-current) `theme.*` constants; `MainWindow._toggle_theme()` calls its own `_refresh_theme_widgets()` and then `refresh_theme()` on whichever of `settings_window`/`products_window`/`history_window` are currently open (each of those, in turn, forwards to any of their own sub-dialogs, e.g. `SettingsWindow.refresh_theme()` → `CalibrationDialog.refresh_theme()`). When adding a new raw-tk widget or a colored Treeview tag anywhere, add it to the owning screen's `refresh_theme()` too, or it will silently keep the old palette's color after a mode switch. `ColorBar._color_for()` re-reads `theme.RED/AMBER/GREEN/IDLE_GRAY` on every call (not a cached dict) specifically so the *currently shown* color re-renders correctly on switch, not just newly-set ones. `dark_mode` persists in `scale_sampler_config.json` and is applied before `_build_ui()` runs (via `theme.set_mode`), so the app opens in the last-used mode.

### Touch sizing

This is a touchscreen kiosk app, so `theme.apply_theme()` sizes every ttk style for a finger, not a mouse pointer: `TButton`/`Accent.TButton` padding `(16, 10)`, `Treeview` `rowheight=36`, `TNotebook.Tab`/`TCombobox`/`TEntry`/`TSpinbox`/`TCheckbutton`/`TRadiobutton` padding, and `Vertical.TScrollbar`/`Horizontal.TScrollbar` widened to `arrowsize=24`/`width=24`. All centralized in one place (the same `ttk.Style()` every screen already reads colors from) rather than per-widget, so a new screen gets touch-sized controls for free just by using plain `ttk.*` widgets — don't hardcode a smaller `width=`/`padding=` on an individual button/entry unless it genuinely needs to be small (e.g. the `?`-sized "⟳" refresh-ports button), since that opts it out of this.

### Hebrew rendering on Linux (`scale_app/rtl.py`)

Tk does not implement the Unicode Bidirectional Algorithm on X11 — unlike Windows, where GDI/Uniscribe reorders RTL runs before Tk ever draws them — so every Hebrew string renders in raw logical (storage) order, which looks mirrored on screen. Confirmed against a real Ubuntu 24.04 box: every Hebrew label/button/column header was reversed while digits and Latin text (`kg`, `COM3`) stayed correct, and the identical build renders correctly on Windows. `rtl.patch()` (called once, from `scale_sampler.py`, before any widget is built) monkey-patches this away for text Tk itself draws: `tkinter.Misc._options`'s `text` key (covers Label/Button/LabelFrame construction *and* `.configure()`, since ttk widget construction funnels through the same classic-tkinter path), `Treeview.insert`/`.item()` (`text=`/`values=`), `Text.insert` (log boxes), and `messagebox._show`'s `message` body text (covers all of showinfo/showerror/askyesno/…). It's a no-op on non-Linux platforms (`rtl.visual()` returns its input unchanged), so this never touches Windows rendering. Requires `python-bidi` (import name `bidi`) — installed by `run.sh`/`install-linux.sh`, Linux-only.

**Three separate ttk option-serialization paths, not one** — missing this cost a whole extra round of hardware debugging. `Misc._options` (widget construction + `.configure()`) is one path; `Treeview.insert`/`.item()` build their Tcl args directly via `_format_optdict`, a second; and `Treeview.heading()` / `Notebook.add()`/`.insert()`/`.tab()` go through `_val_or_dict`→`_format_optdict`, a third. Patching only the first two left column headers (every Treeview in the app) and `SettingsWindow`'s tab labels ("חיבור"/"שקילה"/"דיאגנוסטיקה") reversed even after everything else was confirmed fixed. `rtl.patch()` now covers all three. Any new ttk method found to carry Hebrew text needs its actual serialization path checked in `ttk.py` — don't assume the existing patches cover it just because a *similar-looking* method already does.

**Window titles (`Wm.title()`/`wm_title()`) are deliberately NOT patched**, unlike everything above — the title bar / Alt-Tab preview / taskbar text isn't drawn by Tk at all, the window manager (GNOME Shell/Mutter, via Pango) draws it and already applies the Unicode Bidi Algorithm correctly on its own. An earlier version of this patch touched `Wm.title` too and that was a real, confirmed-on-hardware regression: it bidi-reordered an already-correct string, so window titles showed up reversed while every in-app widget was correctly fixed. **`messagebox._show`'s `title` argument is the same trap in disguise**: it becomes the dialog's actual WM title (the `tk_messageBox -title` option sets the window's real title, not a Tk-drawn label) — confirmed on hardware again, an error dialog's title showed reversed while its `message` body (genuinely Tk-drawn) was correctly fixed by the same patch. `_show()` only reorders `message`, never `title`. If a future symptom looks like "reversed Hebrew, but only in a title bar / window switcher / dialog caption, not inside the window or dialog body" — that's this exact trap, not a reason to re-patch either one.

**Deliberately not patched: `Variable.set()`/`.get()` and Combobox `values=`.** Those back interactive, data-bound widgets whose displayed string gets read back and used as a dict-key/DB-match — reordering it for display would silently break that lookup *only on Linux*, since the reordered string wouldn't equal the original stored key. Found three real instances of this shape (all fixed with an explicit display↔logical translation, not the generic patch):
- `MainWindow.product_combo`/`.product_var` and `HistoryWindow.product_filter_combo` — both build a `values=[rtl.visual(name) for name in names]` list plus a `_display_to_name`/`_product_display_to_name` reverse-map (`{display: original}`, an identity map on Windows), and translate the read-back selection through it *before* using it as a dict key / `db` name match.
- `HistoryWindow.verdict_filter_combo` — same pattern, reverse-mapping the (hardcoded, not DB-sourced) `VERDICT_LABELS` display strings back to their internal `"green"/"red"/"yellow"/"none"` keys.
- `ProductsWindow`'s `ProductFormDialog.name_var` (the product-name `Entry`, editable, not display-only) — pre-filling it with `rtl.visual(product["name"])` so an *existing* Hebrew name displays correctly for editing would otherwise get written back verbatim to the DB (permanently corrupting the stored name) if the user clicks "שמור" without retyping. `_on_save()` guards this: if the field still equals the pre-filled *display* string unchanged, it substitutes back the preserved original name instead of what's in the widget.

Any new Combobox/Entry/StringVar that carries Hebrew content sourced from the DB or matched by string equality needs the same explicit reverse-map treatment — never assume `rtl.patch()`'s generic `text=`/Treeview/messagebox coverage is enough for a widget whose value is read back for logic, not just displayed.

## Protocol notes (see also the module docstring in `scale_app/swan.py`)

- **Swan weight reading (poll mode)**: send a bare `W` (no `\r\n`; a trailing `\r\n` gets interpreted as two separate commands and causes a double response) and read back `<+/-><7 chars><CR>`. The 7 characters are digits with an optional single `.` in any position (or none) — `parse_swan_frame` does not assume a fixed decimal position; if there's no `.` the value is an integer scaled by `/1000`. This is what real Swan heads send in the field — don't tighten it back to a fixed-position regex. `parse_swan_frame` returns a 4-tuple `(weight, status, special, decimals)` — `decimals` is how many digits followed the decimal point *in that specific frame* (e.g. `+00370.0` → 1, not the app's usual 3), so the live weight readout (`MainWindow`'s `"live"` handler, via `formatting.fmt_weight(w, decimals=decimals)`) shows exactly what the device sent (`370.0`) instead of always padding to a fixed precision (`370.000`). This only applies to the live/streaming readout — the *decided* weight after a session (a median across several readings) still uses `fmt_weight`'s default fixed precision, since a computed result has no single "as received" form.
- **Swan continuous streaming (listen mode)**: `WeighingEngine.connect()` sends a single uppercase `S` right after opening the port when `settings.listen` is true, to start the head's continuous broadcast; `disconnect()` sends a single lowercase `s` to stop it before closing. This is tracked via `self._stream_started` (set from `settings.listen` at connect time) rather than re-checking `settings.listen` at disconnect time, so toggling listen/poll mid-session while connected can't leave the head stuck mid-stream.
- **Swan calibration (PC0035)**: a distinct ESC-command protocol (`\x1B\x50`/`\x1B\x4E`/`\x1B\x65`, i.e. ESC P / ESC N / ESC e), only ever used by the calibration wizard.
- Reference docs: `Swan/PC0034.docx` (weight/binary frame) and `Swan/PC0035.docx` (calibration).

## Cross-platform notes

- `theme.maximize(root)` starts truly full-screen (`attributes("-fullscreen", True)`, covering the taskbar/Dock too) rather than plain "maximized" (`state("zoomed")`), falling back to `-zoomed` (Linux/X11) then manual geometry from `winfo_screenwidth/height` if fullscreen isn't supported. Fullscreen removes the OS title bar, so it also binds `<F11>`/`<Escape>` to toggle back to a normal `zoomed` window — and `MainWindow` has its own "✕ סגור" button in the header for the same reason (there's no OS close button while fullscreen).
- `theme.pick_font()` checks `tkfont.families()` at runtime before using a font name, so Windows-only fonts (`Consolas`) fall back to Linux equivalents (`DejaVu Sans Mono`) instead of silently substituting something inconsistent.
- `engine.list_serial_ports()` (wrapping `serial.tools.list_ports`) already returns the right thing on both platforms (`COMx` on Windows, `/dev/ttyUSB0`/`/dev/ttyACM0` on Linux) — no platform branching needed there. It filters out ports whose `description` is falsy or the literal `"n/a"` — on Linux this hides the generic `/dev/ttyS0`..`ttyS31` legacy nodes that always exist regardless of connected hardware and would otherwise flood the Settings port dropdown alongside the one real device.
